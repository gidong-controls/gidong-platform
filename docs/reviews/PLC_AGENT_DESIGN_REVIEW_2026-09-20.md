# PLC 에이전트 설계 반대 검토 — 구현을 다시 막을 모순과 수정 결정

기록 상태: 2026-09-20의 설계 반대 검토. 현재 계약·개발 순서는
[PRD](../../PRD.md)와 [구현 계획 §4·§5](../AGENT_PRODUCT_PLAN.md)를 따른다.
아래 우선순위·완료 상태·compiler/attempt 의견은 해당 날짜의 기록이다.

검토일: 2026-09-20. 대상: [총괄 설계 D1~D8](PLC_AGENT_ARCHITECTURE_2026-09-19.md), [현상태 감사](PLC_AGENT_AUDIT_2026-09-19.md), 현재 소스.

## 1. 판정

**방향은 타당하다. 그러나 9월 19일 계획에는 실제 구현 계약과 맞지 않는 부분과 미결정이 있었다. 그대로 구현하면 또 막힐 수 있었다.** 특히 “기존 compiler 재사용”과 “같은 operation에서 수정·재개”를 무조건적인 지시로 쓰면 안 된다.

- 유지할 방향: 모델이 조사·설계·래더 작성·시험·수정을 판단하고, 기존 Host/도구/영속 작업물을 통해 수행한다. 장비별 정답 수리 절차로 대체하지 않는다.
- 바로잡을 것: 설계 정책과 컴파일의 분리, 작업/실행 시도의 정체성, 요청별 완료 조건, native 변경과 IR의 관계, 시험 판정 기준, 승인 범위, 구현 순서.
- 현재 제품: **다시 실행하기만 하면 자율 완성된다고 판단할 수 없다.** 이번에는 문서만 수정했으며 감사에서 확인된 제품 코드 결함은 남아 있다.
- 다음 구현: 아래 결정에 따라 A→B를 시작할 만큼 구체화했다. B의 실제 수정본 재시험까지 입증하기 전에는 “실행 루프 연결 완료”라고 보고하지 않는다. B만 통과해도 제품 전체 합격은 아니다.

이 문서는 당시 기존 설계의 모순을 정정한 기록이다. 9월 19일 문서와의 비교에서는
이 검토의 의견을 반영했으며, 현재 구현 순서는 위 현행 계획이 관리한다.

### 검토 방식과 한계

사용자가 지정한 Sol medium 작업자 두 명에게 이전 답변 전체를 넘기지 않고, 각각 설계 반대 검토와 native 실행 계약 검토를 맡겼다. 주 에이전트가 핵심 지적을 소스와 대조했다. 이는 서로 다른 관점의 내부 검토이지 외부 인간 전문가의 인증이나 편향 없는 독립 검증이라는 뜻은 아니다.

기준 HEAD는 Platform `9e2b7eb`, Agent `0410ed1`, MCP `dd6b43e`, CLI `00567b5`다. 행 번호는 이 소스 기준 탐색용이며 함수명으로 재검색한다. 9월 19일 공식 웹 벤치마킹은 총괄 설계 문서에 있고, 이번에는 그 원칙이 **우리 실제 구현 계약에 적용 가능한지** 반박 검토했다. 새 모델 실행·XG5000/XG-SIM 시험·물리 PLC 조작은 하지 않았다.

## 2. 구현을 막을 수 있는 지적

### R1 / P1 — 재사용하자는 compiler 자체가 설계 전략을 강제한다

**확인된 사실:** 신규 native 설계의 `native_projects.py::_compile_native_program`은 단순한 참조 해석·명령 변환기가 아니다.

- 2412~2422행: control network 출력의 정확히 하나인 OUT, timer의 정확히 하나인 TON을 요구한다.
- 2477~2494행: 특정 선언의 permit/mode/step 조건을 rung이 정해진 방식으로 보장하는지 검사한다.
- 2560~2576행: signal SET은 reviewed alarm trigger, signal RST는 reviewed recovery rule에 결속되어야 한다.
- 2579~2653행: step 전환과 SET/reset을 선언된 sequence/recovery 구조에 결속한다.

따라서 라우터만 풀어도 일반 내부 상태 SET을 사용하는 다른 설계를 이 컴파일 경로가 거절할 수 있다. “모델의 설계 자유”와 “기존 compiler 전체를 그대로 사용”은 양립하지 않는다. 이 지적은 제품 전체의 모든 편집 경로가 SET을 금지한다는 뜻은 아니다.

**결정:** 참조·타입·주소·지원 명령·lowering/source map은 재사용한다. 장비/설계 전략의 검사는 별도 요구 진단이나 legacy profile adapter로 분리한다. 필요한 동작 요구를 삭제하지 말고 특정 rung 모양과 구분한다. 기존 저장본은 adapter로 읽되, 신규 범용 작성 경로에 그 형태를 강제하지 않는다.

언어 검사를 전부 없애는 수정은 불합격이다. 동등한 동작을 가진 두 설계가 특정 템플릿 차이만으로 거절되지 않는지 시험한다. 현재 `api_models.py` 402~457행의 조건/action 표현은 제한된 명령 집합이다. 모든 LS 프로그램을 이미 읽고 쓸 수 있다고 주장하지 않는다. 필요한 명령은 언어와 도구 능력으로 확장하며 장비별 정답 함수로 대신하지 않는다.

### R2 / P1 — 같은 작업을 유지하는 것과 같은 native operation에 새 소스를 넣는 것은 다르다

**확인된 사실:** `native_projects.py` 4076행 `replay_if_exists`, 4108행 `create`는 같은 operation의 다른 request/digest를 거부한다. 4406행 `_continue_completed_verification`은 저장된 build를 **재생성하거나 소스 편집하지 않고** 이어간다고 명시한다.

3958행 `prepare_simulation_plan_revision`도 소스 수정 경로가 아니다. 3993행은 compiled 결과가 같아야 하고, 4031~4049행은 `indexAcceptanceBindings` 외 실행 설계 변경을 거절한다. 4051~4074행의 권한은 그 동일 build의 시뮬레이션 검증에 한정된다.

Agent가 draft만 고친 뒤 기존 resume을 호출하면 이전 프로그램을 다시 시험한다. 수정된 plan을 overlay로 넘기면 거절되고, 파일만 다른 경로로 바꾸면 기존 hash가 stale해진다. “resume 연결”만으로 수정 루프가 생기지 않는다.

**결정:** 유지하는 것은 사용자 작업과 working copy다. 실행 소스 변경마다 새 immutable 실행 시도/변경 transaction과 그 소스의 결과를 만든다. 동일 operation resume은 **동일 실행 소스의 중단 복구/후속 검증**에만 사용한다. 새 operation을 만들라는 말도 매번 새 프로젝트 파일을 만들라는 뜻이 아니다.

### R3 / P1 — 강제 publish를 없애는 것만으로 목표와 완료가 생기지 않는다

**확인된 사실:** Agent `runtime.py` 16686행은 신규 planning을 일반 루프에서 분기한다. 19365행은 설계 도구만 남기고, 19482~19485행은 native 실행을 금지하며 publish 뒤에만 완료하도록 한다. 19568행 이후는 발행 시 graph를 종료한다. 프롬프트에서 자율성을 강조해도 이 수명주기는 바뀌지 않는다.

**결정:** 기존 `AgentRuntime.run`의 일반 엔지니어링 루프를 기준으로 설계 workspace를 도구 능력으로 연결한다. 도구 목록만 늘리거나 planning 전체를 또 다른 외부 LLM 루프로 감싸지 않는다. 요청별 결과, artifact 반환, 실패 관측, 중단/재개 상태까지 같은 run 계약으로 정리한다. “계획만” 요청은 실제로 계획만 끝낼 수 있어야 한다.

Agent가 다음 행동과 완료 설명을 결정한다. Host는 근거의 대상/최신성, 알려진 미완료, 실행 범위 일치를 확인한다. Host에 새 장비별 완료 순서도를 넣지 않는다. 최소 완료 계약은 3절과 같다.

### R4 / P1 — “IR이 원본”만으로 기존 native 편집과 충돌을 해결할 수 없다

**위험:** 현재 실행된 프로그램과 Agent가 수정 중인 IR은 다른 revision일 수 있다. XG5000에서 사용자가 직접 바꾼 뒤 오래된 IR을 덮어쓰면 작업을 잃는다. 반대로 파일이 바뀌었다는 이유만으로 과거 설계와 시험 결과를 새 프로그램에 적용해서도 안 된다.

**결정:** 편집 중 의도된 소스와 실제 native 소스의 identity를 함께 추적한다. “원본 하나”는 하나의 실행 의미를 여러 문서에서 독립 작성하지 말자는 뜻이지, 변경 중 draft와 실제 파일이 항상 같다는 뜻이 아니다. 읽기/적용 전 baseline을 비교한다. 외부 변경은 읽어서 새 기준으로 채택하거나 diff를 조정한다. 충돌 시 필요한 선택만 묻는다.

지원하지 않는 native 요소를 조용히 지우는 lossy import는 금지한다. 기존 읽기 경로와 원자적 편집을 재사용하고, lossless round-trip 가능한 범위를 확인한다. 신규 작성만 지원하는 표현을 기존 프로젝트 전체 편집 지원으로 보고하지 않는다.

### R5 / P1 — Agent가 구현과 시험 기대값을 함께 고치면 가짜 완료가 가능하다

**위험:** “기대값을 약화하지 말라”는 프롬프트만으로는 충분하지 않다. 기존 감사에서도 8개 시험 통과와 미검사 수동 운전 반례가 공존했다. 모델이 고친 프로그램의 동작을 그대로 기대값으로 삼으면 자기 일관성만 확인한다.

**결정:** 사용자/자료에서 채택한 요구와 그 출처·revision, 요구에서 도출한 필수 동작 주장, 실행 입력·실제 관측을 구분한다. 필수 주장은 구현 수정 때문에 사라지지 않는다. Agent는 시험과 반례를 추가하고 잘못된 바인딩을 고칠 수 있지만, 요구나 기대값 변경의 근거와 영향은 남긴다. 미해결 요구를 단순히 완료 범위에서 빼지 않는다. 원래 요구가 불명확하거나 바뀌는 경우만 사용자 판단으로 되돌린다.

시험 성공은 실제 observer가 읽은 값이며, 모델의 평가 문장과 구분한다. 요구 revision·시험 정의·실제로 저장/실행된 source identity를 결속한다. 수동 운전 중 모드 전환과 stop 해제 재기동 반례를 넣은 잘못된 후보가 실제로 실패하는지 확인하여 판정 기준 자체도 검증한다. 독립 검토 Agent의 찬성은 실행 관측을 대체하지 않는다.

### R6 / P1 — plan 검토와 파일 변경 권한을 혼동하면 반복 승인 또는 권한 우회가 된다

**결정:** 사용자 작업 범위, 기술적으로 검증된 candidate, Host가 발급하는 정확한 변경 권한을 구분한다. 자연어 요청과 제품 설정으로 특정 작업 사본에서의 작성·저장·시험 범위를 정하고, 그 안에서 정상적인 수정 반복을 진행할 수 있게 한다. 사용자가 매번 금지 문구나 수백 개 ID를 입력하지 않게 한다.

기존 승인 receipt를 재사용하거나 Agent의 publish를 사람이 검토했다는 기록으로 위조하지 않는다. 작업 범위에 근거한 권한 발급 정책을 명시적으로 구현·시험한 뒤에만 반복 승인을 줄인다. 현재 승인 검사를 먼저 지우고 나중에 경계를 붙이지 않는다. 다른 파일/원본 덮어쓰기·물리 PLC 등 범위 확장은 별도 판단이다. 이번 구현 범위는 오프라인 XG5000/XG-SIM이다.

### R7 / P2 — 수직 경로 우선이라면서 전면 개편을 한 번에 요구하면 다시 끝나지 않는다

기존 계획은 한 경로를 먼저 만들자고 하면서 루프·IR·모든 장비·모든 모델·UI를 한 완료 묶음으로 나열했다. 최종 제품 기준으로는 필요하지만 첫 구현의 경계와는 구별해야 한다.

**결정:** 4절 A~D로 구현 증거를 누적한다. 각 단계의 성공을 제품 전체 완료로 부풀리지 않는다. 다음 단계가 남아 있는데 단위 테스트만 늘리며 같은 단계를 반복하지 않는다. 실패하면 최초로 끊긴 경계와 해당 artifact를 좁혀 수정한다. 판정표를 추가하는 것 자체가 구현 성과가 되어서는 안 된다.

## 3. 이번 검토로 확정하는 최소 계약

아래는 기존 run/draft/workspace/change transaction/native operation/evidence에 연결할 논리 정보다. 새 mission 서비스나 병렬 DB를 모두 만들라는 스키마 지시가 아니다. 기존 generic `design.edit`는 변경 묶음을 적용한 뒤 검증하는 경로가 이미 있다(`planning_drafts.py` 8568~8644행). 편집기부터 재발명하지 않는다.

### 목표와 완료

| 사용자 요청 | 요청을 끝냈다고 설명하기 위한 결과 | 자동으로 추가하지 않을 일 |
|---|---|---|
| 설명/조사 | 해당 소스를 읽은 근거와 정확한 설명, 모르는 범위 | 파일 변경·강제 시험 |
| 설계/후보만 | 편집 가능한 설계 산출물과 남은 결정·제약 | native 적용 |
| 만들고 저장 | 목표의 실행 소스, 실제 저장본과 적용/readback 근거, 가독성 | 물리 PLC 다운로드 |
| 동작까지 확인 | 위 산출물과 해당 revision의 요구별 실제 시험 결과, 입력 복원/STOP 결과 | 다른 소스의 과거 시험 성공 차용 |
| 기존 프로젝트 변경 | baseline 보존, 요청한 diff의 적용/저장, 영향 범위에 맞는 검증 | 항상 새 프로젝트부터 작성 |

표는 사용자에게 선택하게 할 하단 모드 메뉴가 아니다. Agent가 자연어 요청과 현재 작업 맥락에서 범위를 해석하고, 큰 차이를 만드는 모호함만 묻는다. 이미 약속된 “만들고 동작 확인”을 “설계만”으로 축소하지 않는다.

현재 목표·대상 working copy·필요 결과·충족 근거·남은 일·중단 이유를 보존한다. 목표 충족 설명과 도구/Host가 기록한 실행 사실이 모두 있어야 한다. 예산/시간 소진·취소·도구 실패는 그 상태 그대로이며 완료가 아니다. 완료 뒤 후속 변경은 이전 작업물을 재사용하되 영향받은 결과를 새 revision에서 다시 확인한다.

### 실행 identity와 재개

```text
같은 사용자 작업 / 같은 working copy
  요구 revision ── 의도된 소스 revision ── 변경/실행 시도
                                               │
                                  실제 저장·readback identity
                                               │
                            그 identity + 시험 정의의 실행 관측
```

- 실제 내용이 다른데 revision 번호만 같거나, native 파일 hash만 같고 대상 program/bindings가 다르면 같은 시험 대상이 아니다. 기존 source/IR/project digest와 대상/설정 결속을 활용한다.
- 의미 있는 소스 변경은 새 candidate/transaction/실행 결과로 남긴다. 과거 기록은 불변이다. 기존 동일 소스의 상태 조회·재열기·resume은 재사용한다.
- 재시험은 **의도한 실행 revision/digest**를 받거나 동일한 강도로 결속해야 한다. draft 수정만으로 native가 바뀐 것으로 처리하지 않는다.
- 중단 뒤에는 저장된 핸들과 실제 상태를 먼저 읽는다. 작업이 이미 반영되었다면 중복 적용하지 않고 이후 필요한 일을 판단한다. 결과가 불명확한 비멱등 동작은 성공/실패 어느 쪽으로도 추정하지 않는다.
- 외부 수정, metadata-only 변경, 실행 소스 변경을 구분한다. 무조건 과거 시험을 모두 재실행하거나 무조건 모두 재사용하는 두 극단을 피한다. 재사용은 요구/실행 의미/시험 결속의 동일성을 입증한 범위에 한한다.

## 4. 다음 구현 순서와 단계별 종료선

### A — 범용 작성과 작업 제어권 복구

변경: 기존 일반 루프와 설계 도구를 연결하고 valid/publish 강제 종료를 제거한다. 최소 목표/권한/결과 계약을 기존 상태에 연결한다. R1의 언어 검사와 설계 정책을 분리하며 legacy 저장본 호환을 유지한다. generic atomic edit를 재사용한다.

증거: valid 뒤 read/edit 가능, plan-only 요청은 실행하지 않음, 예산 종료는 미완료, 일반 내부 상태를 쓰는 지원 가능한 두 설계가 템플릿 차이만으로 거절되지 않음. 잘못된 참조/타입·권한 범위 위반은 계속 거절됨. 의미 반례 회귀는 감사 F4/F5의 기존 산출물에서 가져온다.

여기서 끝내지 말고 B로 간다. UI 전면 재작성, 신규 프레임워크 교체, 모든 기종 지원은 A의 선행 조건이 아니다.

### B — 가장 위험한 native 수정·재시험 연결을 먼저 입증

이것은 모델에게 항상 따르게 할 고정 workflow가 아니라, 실패 수정 능력을 확인하는 인수 시험이다. Agent가 실패 원인과 수정 방법을 선택하며 제품 밖의 사람이 내부 ID·repair 호출 순서를 대신 써 주지 않는다.

증거는 네 가지다.

1. 잘못된 저장본에서 지정한 요구 반례가 실패한다.
2. Agent가 수정한 소스의 digest가 실제 native 저장/readback과 결속된다.
3. 새 시험은 그 수정본을 실행하고, 기존 실패가 해소되며 필수 요구를 삭제하지 않았다.
4. 이전 receipt를 새 수정본의 성공으로 재사용하려 하면 거절된다. 적용 이후 중단·재개도 중복 적용하지 않는다.

B의 실패를 라우터 프롬프트 수정이나 단위 테스트 수로 덮지 않는다. 어떤 경계가 끊겼는지 candidate/transaction/readback/관측으로 특정한다. B가 통과하면 같은 기반으로 C로 간다.

### C — 일반 사용자의 대동인덱스 완성 경로

자연스러운 최초 요청부터 새 작업 사본을 만들고, 필요한 설비 정보만 질문하며 실제 설계·래더·저장·동작 검증까지 진행한다. 감사 10절의 양방향 모드 전환, 수동 입력 순서, 정지·알람·reset·카운터/타이머 반례를 실제 새 프로그램에서 확인한다. 심볼·주석·타입·네트워크 설명은 저장/재열기된 native에서 읽혀야 한다.

후속 자연어 변경과 설명, 중단 후 재개, 직접 native 편집 후 충돌 처리를 확인한다. 메인 UI는 결과/현재 행동/필요 결정 중심으로 연결하고 내부 ID는 상세로 둔다. 사용자에게 수리 지시문·원본/물리 PLC 금지 문구를 매번 입력시키지 않는다.

한 번의 데모 성공으로 자율성을 보장하지 않는다. 고정 요구와 환경을 기록하고 별도 사본의 독립 실행, 외부 개입 여부, 실패 원인, 결과 품질을 함께 확인한다. 통과 횟수만으로 일반화 확률을 주장하지 않는다.

### D — 일반화·호환성과 최종 인계

index가 아닌 컨베이어 또는 2실린더 등 독립 장비 사례, ID/주소 변화, 전용 repair 없이 일반 편집하는 경우를 같은 능력으로 수행한다. 기존 장비 강제 정책의 호출자를 확인하며 중복 경로를 줄이고 legacy 자료/사용자 이력은 보존한다.

선택된 실제 OpenAI-compatible 서버와 다른 실제 endpoint의 도구 왕복·오류 수정·재개를 확인한다. transport 적합성과 모델의 설계 품질은 따로 보고한다. 200k급 문맥 처리 요구는 서버 실제 지원 한도/입력/회수 정확성으로 확인하며 코드 상수나 장시간 동작만으로 통과 처리하지 않는다. 지원하지 않는 서버에는 지원한다고 거짓 표시하지 않는다.

최종 완료는 감사 10절 + 이 문서 B의 수정본 identity + C의 실사용 결과가 모두 맞는 상태다. 플랫폼의 모든 미래 기능이나 모든 모델의 동일한 PLC 품질을 보장한다는 뜻은 아니다. 현재 요청 범위의 실패/미검증은 그대로 남기고, 완료를 위해 판정 범위를 사후 축소하지 않는다.
