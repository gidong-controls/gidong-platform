실행 순서·구조 시험 의견은 당시 기록이며 현재 작업 목록을 덮어쓰지 않는다.

작성·웹 확인: 2026-09-19.

2026-09-20: [설계 반대 검토와 수정 결정](PLC_AGENT_DESIGN_REVIEW_2026-09-20.md)을 반영했다.

## 1. 제품 정의와 설계 책임

**우리가 만드는 것은 PLC 엔지니어링 에이전트다. 모델이 요구를 이해하고, 프로젝트를 조사하고, 제어 로직을 설계·작성하고, 도구로 실행하고, 결과를 해석하여 수정과 완료 여부를 판단해야 한다.**

“오류 코드 A이면 수리 함수 B, 검사 통과이면 발행”이라는 장비별 절차를 연결하고 모델에 빈칸을 채우게 하는 것이 목표가 아니다. 여러 역할을 수행하는 것 자체가 문제도 아니다. 그 역할을 수행할 작업 공간·도구·관측·지속성이 있어야 한다.

총괄 설계에서 해결할 질문은 개별 rung 하나의 정답보다 넓다.

1. 누가 다음 행동과 설계 방식을 결정하는가?
2. 무엇이 실제 프로그램이며, 다른 표현은 어떻게 일치하는가?
3. 실행 실패를 에이전트가 이해하고 수정할 수 있는가?
4. 중단·장문·다른 모델에서도 같은 작업물을 이어갈 수 있는가?
5. 사용자에게 읽을 만한 결과를 주며, 실제로 요청한 일을 끝냈는가?

최종 PLC 프로그램의 실행은 명확하고 결정적이어야 한다. **개발 에이전트의 판단을 룰베이스로 대체하지 말자는 것과, PLC 실행·컴파일·저장을 정확한 코드로 구현한다는 것은 양립한다.**

## 3. 모델과 결정적 코드의 책임을 구분한다

| 책임 | 담당 | 하지 말아야 할 대체 |
|---|---|---|
| 요구 해석, 필요한 질문, 조사 순서 | Agent | 모든 요청을 무조건 신규 계획 작성으로 변환 |
| 모드·시퀀스·인터록·복구의 설계 방식과 래더 작성 | Agent | 장비 이름/특정 ID에 따라 Host가 정해 둔 회로를 삽입 |
| 원인 가설, 읽을 범위, 수정 범위, 다음 시험 선택 | Agent | 오류 코드마다 한 가지 repair만 허용 |
| 자료·명령어·현재 프로젝트의 검색과 읽기 | 도구, 선택은 Agent | 프롬프트의 기억이나 전체 JSON 재출력에 의존 |
| 타입·참조·명령어/주소 지원, 동시 편집 충돌 | Host/컴파일러 | 검사를 모두 제거하거나 일관성 오류를 모델 말로 승인 |
| 승인된 범위의 파일 조작·빌드·저장·시뮬레이션 | Host → MCP/CLI | 모델이 직접 DB 상태/시험 성공 receipt를 작성 |
| 요구 충족 여부에 대한 설계 판단 | Agent, 필요 시 독립 검토 | 구조 검사 성공을 기능 요구 전체 충족으로 바꿈 |
| 무엇이 실제로 실행됐는지에 대한 사실 | 실행 도구와 기록 | 모델의 “통과했다”는 문장으로 관측을 대체 |
| 사용자 목표에 대한 완료 설명 | Agent, 실제 산출물·관측에 근거 | 발행 성공·호출 한도·run 종료를 모두 제품 완료로 표시 |

Host의 규칙은 실행 경계와 언어/데이터의 일관성을 보장한다. 특정 설계 전략만 정답으로 인정하여 다른 올바른 PLC 구현을 막지 않는다. 예를 들어 상호 배제는 요구사항일 수 있지만, 반드시 특정 이름의 bit와 특정 모양의 rung으로 구현하라는 것은 다른 문제다.

## 4. 목표 아키텍처

다음은 구현할 책임 구조다. 모든 요청에 아래 노드를 순서대로 통과시키는 고정 workflow가 아니다.

```text
사용자 목표 / 현재 프로젝트 / 후속 지시
                   │
                   ▼
          주 엔지니어링 Agent
  이해·설계·조사·작성·진단·수정·완료 판단
       ↕                    ↕
지속되는 프로젝트 상태    조합 가능한 엔지니어링 도구
요구/소스/revision         조회·검색·부분 편집·참조 검색
변경/작업 메모             컴파일·저장·재열기·시뮬레이션
관측/남은 일                       │
       ▲                           ▼
       └──── 실제 결과 ── Host → MCP/CLI → XG5000/XG-SIM

UI: 사용자에게 결과·변경·필요한 결정을 보여 줌
    내부 ID/trace는 필요할 때 펼쳐 봄
```

주 Agent 하나로 경로를 먼저 완성한다. 독립적인 문서 조사나 설계 검토에 도움이 될 때 하위 Agent를 사용한다. 다수 에이전트를 고정 배치하거나 역할별 순서도를 추가하는 것만으로 작업 제어권 문제가 해결되지는 않는다. 동일 프로젝트의 동시 쓰기는 revision/transaction으로 조정한다.

### D1. 사용자 목표와 run/발행 상태를 분리한다

새 프로젝트 설명 요청, 설계안 요청, 실제 구현 요청은 완료 범위가 다르다. 사용자 목표·선택된 작업물·남은 결과를 기존 영속 상태에 연결한다. 새 mission 프레임워크를 하나 더 만드는 것은 우선순위가 아니다.

요청별 필요한 산출물·실제 근거·남은 일·중단 이유를 보존한다. Agent가 완료 설명을 판단하고 Host는 근거의 대상/최신성과 알려진 미완료·권한 범위 불일치를 확인한다. 사용자가 작업 유형을 기술 메뉴에서 매번 선택할 필요는 없다. 구체적인 최소 계약은 [반대 검토 3절](PLC_AGENT_DESIGN_REVIEW_2026-09-20.md)에 있다.

`design.check=valid`는 관측 하나다. Agent는 계속 읽고, 비교하고, 고칠 수 있다. 구조 검사는 편집 때 실행하거나 도구 내부에서 검사할 수 있지만, 이를 이유로 다음에 읽기/수정 도구를 없애서는 안 된다. 발행은 설계 산출물 작업이지 보편적인 종료 조건이 아니다.

### D2. 계획과 native 실행 사이를 같은 에이전트 작업으로 연결한다

기존 일반 엔지니어링 루프에 설계 workspace와 create/check/save/reopen/simulation 능력을 연결한다. planning 전용 루프에 도구만 추가하거나 바깥에 별도 LLM 오케스트레이터를 하나 더 만들지 않는다. plan-only 요청과 실제 구현 요청의 수명주기/결과 반환을 구분한다.

사용자 작업 범위, candidate의 기술 검토, 정확한 변경 권한은 구별한다. 작업 사본 안의 정상적인 수정 반복은 승인 범위에 따라 이어가되 이전 receipt나 simulation review를 새 소스 쓰기 권한으로 재사용하지 않는다. 원본/다른 대상/물리 PLC 등 범위 확장은 별도다. [반대 검토 R2·R6](PLC_AGENT_DESIGN_REVIEW_2026-09-20.md)의 확인된 계약을 따른다.

실패에서 반환할 정보에는 대상 revision, 실제 수행 여부, 오류 위치, 기대/관측 값, 관련 artifact 조회 참조가 포함되어야 한다. 핵심 관측은 즉시 주고 긴 trace는 추가로 읽게 한다. 결과가 불명확한 저장/생성 동작은 현재 상태를 조회한 뒤 이어간다. 이 처리는 중복 실행 방지이지 특정 PLC 로직을 선택하는 규칙이 아니다.

### D3. 실행 의미의 원본을 하나로 정한다

현재 선언·모드·sequence·control network·rung에 같은 의미가 중복된다. 모두를 모델이 독립적으로 재작성하고 검사기가 서로 맞추게 하는 상태를 유지하지 않는다.

기본 설계 결정은 다음과 같다.

- typed symbol/주소 선언과 **Agent가 작성·편집하는 ladder IR**을 실행 소스의 기준으로 삼는다.
- 요구사항과 시퀀스 설명은 의도와 제약이다. 그것이 실행 소스와 충돌하면 Agent가 차이를 읽고 수정한다. 설명이 있다고 실제 동작이 구현되었다고 간주하지 않는다.
- sequence/macro 작성 기능을 유지한다면 명시적 lowering 단계에서 rung과 source map을 만든다. 같은 로직을 상위/하위 표현에서 동시에 독립 수정하게 하지 않는다. 상세 전환 정책은 명시적으로 드러나야 한다.
- 래더를 특정 순차 제어 템플릿으로 제한하지 않는다. 지원하는 PLC 명령·참조의 범위 안에서 Agent가 다른 올바른 구조도 작성할 수 있어야 한다.
- 기존 compiler의 참조/타입·주소·명령 변환과 native bridge는 재사용한다. 다만 현재 `_compile_native_program` 안의 alarm 전용 SET, recovery 전용 RST, sequence 형태 강제는 범용 언어 계약이 아니다. 설계 정책을 요구 진단/legacy adapter로 분리한다. compiler 전체를 그대로 유지하거나 모든 검사를 삭제하는 두 방식 모두 이 결정이 아니다.

구체적인 스키마 변경은 기존 저장본과의 호환·round-trip을 확인하며 적용한다. 선언 rename, 타입 변경, 네트워크 이동, 관련 참조 편집은 하나의 일관된 변경으로 수행할 수 있어야 한다.

편집 중 IR은 의도된 revision이고 native readback은 실제 적용된 revision이다. 두 identity와 변환 관계를 보존한다. 사용자가 native에서 직접 바꾸면 baseline drift를 읽어 채택/조정하며 오래된 IR로 덮어쓰지 않는다. 지원하지 않는 native 요소를 조용히 버리는 import도 하지 않는다. 현재 표현의 지원 명령 범위를 명시하고 필요한 명령은 일반 능력으로 확장한다.

### D4. 도구는 정답 수리 버튼이 아니라 엔지니어의 작업 능력이어야 한다

기존 도구를 다음 능력으로 정리한다. 아래는 새 API 이름을 모두 만들라는 목록이 아니라, 노출된 도구가 갖춰야 할 능력이다.

| 능력 | 모델이 할 수 있어야 하는 일 |
|---|---|
| 프로젝트 탐색·검색 | IO, program/network/rung, 사용처, 진단, 변경 이력의 관련 부분 찾기 |
| 부분 읽기·비교 | 현재/과거 revision과 실제 native readback의 차이 확인 |
| 일관된 편집 | signal 선언/참조와 rung 조건/action을 함께 변경, 삭제·이동·rename |
| 지식 조회 | 정확한 기종의 명령·주소·타이머·S-step 의미 및 공식 자료 조회 |
| 실행 | 현재 작업물의 빌드/검사/저장/재열기/시험, 진행 중 작업 조회·중단·재개 |
| 관측 | 어떤 입력을 어느 시점에 넣었고 어떤 상태/출력이 관측됐는지 조회 |

일반 편집·실행 도구로 해결할 수 없는 것을 `repair_index_새증상` 하나로 계속 메우지 않는다. 전용 helper는 선택적 자동화로 남길 수 있지만, 그것만 호출해야 다음으로 갈 수 있게 해서는 안 된다.

### D5. 검증은 설계 의미를 관측하고, 구현 방식을 고정하지 않는다

독립적으로 구분할 세 층이 필요하다.

1. 언어/구조: 타입, 참조, 지원 명령, 주소, 컴파일 결과.
2. 요구 기반 동작: 예를 들어 “이동 중 모드 유지”, “새 누름 없는 재시작 금지”. 특정 bit 이름이나 rung 모양을 정답으로 요구하지 않는다.
3. 실제 결과: 저장된 native 프로그램에서 입력·출력·상태의 시간 순서를 관측한다.

Agent는 요구에 맞는 시험을 구성하고 추가 반례를 찾을 수 있어야 한다. 시험 runner는 재사용 가능한 입력·대기·관측 기능을 제공한다. 기존 index profile은 회귀 fixture이지 새 기계의 설계 언어가 아니다. 시험 실패를 없애기 위해 기대값을 약화하거나 요구를 삭제하는 것은 수정이 아니다.

요구의 출처/revision, 필수 동작 주장, 시험 정의, 실제 실행 소스/관측을 연결한다. Agent가 바인딩이나 시험을 고칠 수는 있으나 구현에 맞추어 요구를 조용히 바꾸지는 못한다. 기대값 변경에는 요구 근거와 영향이 남아야 한다. 잘못된 후보가 실제로 실패하는 반례로 시험 판정 기준도 확인한다. 과거 receipt는 소스/요구/시험 결속이 달라진 수정본의 성공을 증명하지 않는다.

별도 검토 Agent는 반례를 찾는 데 사용할 수 있지만, 그 Agent의 동의가 시뮬레이션 관측을 대체하지 않는다. 반대로 몇 개의 시험 통과가 무조건 모든 요구의 완전한 증명인 것도 아니다.

### D6. 장문/재개는 큰 응답이 아니라 지속되는 작업 상태로 해결한다

확정 요구, 현재 소스, 설계 결정, 실제 실행 결과, 남은 일을 기존 store에 보존하고 필요한 부분을 다시 읽게 한다. 프롬프트에는 현재 revision/작업 목표/관련 변경/관측 요약을 제공한다. 상세를 줄여 전달했다면 다시 읽을 경로가 있어야 한다.

200k급 컨텍스트 지원 요구를 임의의 작은 전체 작업 한도로 치환하지 않는다. 동시에 모든 도구 호출마다 200k를 채우거나 한 응답으로 전체 프로젝트를 재출력할 필요도 없다. 모델/서버가 실제 지원하는 문맥·출력 한도와 작업 전체의 지속성은 구분한다. 현재 코드의 `MODEL_CONTEXT_WINDOW_TOKENS=196_608`만으로 실제 200k 처리 능력이 검증됐다고 말하지 않는다.

호출/시간/비용 한도는 투명한 운영 장치다. 도달하면 남은 일과 재개 상태가 보존되어야 하며 완료로 바뀌면 안 된다. 반복 검사는 상태 변화·새 관측이 있는지로 진단하고 Agent가 다른 접근을 택할 수 있게 한다. 무한 재시도도 해결책이 아니다.

### D7. OpenAI-compatible은 전송 계약이며 제어 정책은 모델 이름에 종속시키지 않는다

메시지/도구 호출·결과 대응, streaming, 오류, context/output 한도, 지원 기능을 provider adapter에서 다룬다. 모델별 차이는 명시적 capability로 격리하고, Qwen이니까 특정 단계에서 무조건 특정 수리만 시키는 것으로 해결하지 않는다.

모든 compatible endpoint가 같은 도구·추론 능력이나 PLC 품질을 제공한다고 보장할 수는 없다. 실제 서버로 왕복·실패 수정·재개를 검증하고, 미지원 기능은 정확히 드러낸다. 기존 모델 선택 요구는 유지하되 모델 교체로 F1/F2 같은 구조 결함을 가리지 않는다.

### D8. 사람이 읽을 수 있는 결과까지 에이전트의 작업 범위에 넣는다

사용자는 자신의 설비와 결과를 다루어야 한다. 기본 UI에는 자연어 요청, 실제 작업 진행, 수정 내용, 필요한 선택, 열어 볼 프로젝트가 보여야 한다. 내부 검증 ID는 기술 상세로 둔다.

native 파일의 심볼·주석·네트워크 설명은 결과물이다. 생성 전 문서에 이름이 있다는 것으로 끝내지 않고 저장/재열기한 파일에 반영되어야 한다. 이름·상태·카운터 타입·미사용 선언 정리 역시 작성/수정의 일부다. Agent가 설명만 길게 쓰고 실제 래더는 난독 상태로 남기는 것을 완료로 인정하지 않는다.

| 변경 축 | 기존 위치 | 목표 |
|---|---|---|
| 제어권/종료 | Agent `runtime.py`: `_route_design_workspace_tool`, `_RequireWorkspaceToolUntilPublished`, `_run_design_workspace` | 관측을 모델의 다음 판단으로 돌려주고 발행 강제 제거 |

기존 동작 기반을 한 번에 삭제하지 않는다. [반대 검토 4절](PLC_AGENT_DESIGN_REVIEW_2026-09-20.md)의 순서는 A: 제어권·언어/정책 경계, B: 수정된 native 소스의 실제 재시험, C: 자연어 대동인덱스 완성과 가독성, D: 일반화/호환성·인계다. A의 언어/정책 분리는 B를 가능하게 하는 선행 변경이며, 장비별 강제 정책의 나머지 호출자와 중복 경로 정리는 실제 경로를 확인하며 진행한다. 단계 완료를 제품 완료로 보고하지 않는다.

프레임워크 교체는 현재 경계에서 해결할 수 없는 구체적인 근거가 있을 때 별도 결정한다. 이번 벤치마킹은 “OpenHands/Codex SDK를 설치하면 해결”이라는 결론이 아니다.

## 6. 룰베이스 우회가 아닌지 확인할 구조 시험

이 시험은 기존 감사의 실제 동작 판정표에 추가한다. 별도 거대한 평가 서비스를 만드는 지시가 아니다.

| 시험 | 드러내려는 문제 / 합격 조건 |
|---|---|
| `design.check`는 valid인데 요구 위반이 있음 | Agent가 다시 읽고 일반 도구로 수정할 수 있어야 함. publish만 가능하면 실패 |
| signal ID·주소·station 수가 달라짐 | 의미가 같은 요구는 특정 문자열 repair 없이 해결해야 함 |
| 장비가 index가 아닌 conveyor/2실린더임 | 같은 읽기/편집/빌드/관측 능력으로 해결. 새 장비 정답 함수를 Host에 추가해 통과시키지 않음 |
| 기존 전용 repair helper를 사용하지 않음 | 일반 도구 경로로 확인된 반례를 고칠 수 있어야 함. 이 통제 조건은 시험용이지 제품에서 모든 helper를 금지하는 정책이 아님 |
| 동등하게 올바른 다른 래더 구조 | 특정 템플릿 모양과 다르다는 이유로 의미적으로 맞는 프로그램을 거절하지 않음 |
| 실제 시뮬레이션 실패 | 실패 입력·관측을 읽고 수정/재실행. 사람이 내부 ID와 수정법을 후속 USER 메시지로 써 주지 않음 |
| 중간 중단 후 재개 | 같은 사용자 작업/working copy에서 이어가고 완료된 부작용을 중복 실행하지 않음. 동일 operation은 동일 소스에만 재사용하며 소스 변경은 새 실행 identity로 시험 |
| 새 자연어 후속 변경 | 기존 프로젝트를 읽고 요구에 맞는 범위만 수정. 무조건 새 계획부터 시작하지 않음 |
| 다른 compatible endpoint | 도구/관측 계약을 유지. transport 오류와 모델의 설계 오류를 구별하여 보고 |

동일 입력·동일 모델/설정·깨끗한 별도 작업 사본으로 기존과 새 경로를 비교한다. 성공 여부뿐 아니라 외부 개입, 불필요한 전체 재작성, 같은 오류 반복, 총 시간과 비용, 산출물 가독성을 함께 기록한다. 합격 사례만 골라 에이전트 일반화로 보고하지 않는다.
