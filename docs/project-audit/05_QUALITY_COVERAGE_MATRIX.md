## Finding 상세 — 품질·운영

### AF-07 — 행동 테스트가 CI 인수 경계에 없음

- **문제·증거/코드:** Platform/Agent/MCP `.github/workflows/quality.yml`은 compile/lint/contracts/typecheck/build 중심이며 pytest/unittest 실행 step이 없다(E09). scoped test 파일은 Host26/Agent19/MCP15/CLI2(C07); 실행/통과 개수가 아니다. `test_workspace_stable_workbench.py:31`은 valid→publish-only 기대값(E04).
- **사용자/사업 영향:** 녹색 CI가 Agent 동작/요구 충족을 뜻하지 않는다. **기술 영향:** 제품에 맞지 않는 기대값과 회귀가 유지될 수 있음.
- **심각도/발생 가능성/신뢰도:** P0 / 지속적 / 확인됨·높음.
- **근본 원인:** 정적 품질 gate와 사용자 결과 인수의 분리 부족. **임시 대응:** CI와 native acceptance 범위를 보고에 명시. **근본 해결:** 제품 계약에 맞는 pytest 회귀를 실패 주입으로 검증하고 CI에 실제 수집·실행; GUI/native는 별도 명시 gate.
- **요구/작업:** REL-03,EXE-01/05/08 → RB-04/05/15. 함수형 pytest를 `unittest discover`만으로 검증했다는 주장은 금지.

### AF-08 — 모델 credential/header의 평문 저장

- **문제·증거/코드:** `host/src/controlstudio_host/model_connection.py:154~199`의 JSON 직렬화/역직렬화가 API key 및 custom headers를 `store.py:559~578`의 `secret_payload_json`에 저장(E10). 실제 DB credential 내용은 조회하지 않았다.
- **사용자/사업 영향:** DB/백업을 읽을 수 있는 주체에게 자격증명이 노출될 위험. **기술 영향:** redaction과 API 응답 마스킹이 at-rest 보호를 대체하지 못함.
- **심각도/발생 가능성/신뢰도:** P1 / 로컬 파일·백업 접근 조건부 / 구현 확인됨·높음, 실제 유출 미확인.
- **근본 원인:** 설정 저장이 secret 수명주기와 분리되지 않음. **임시 대응:** DB/백업 공유 금지·접근 최소화, 의심되는 노출은 소유자가 credential 교체 판단. **근본 해결:** OS-backed secret storage/opaque reference 및 기존 값 이동·실패 rollback·삭제 절차. 이번에는 이동/회전하지 않음.
- **요구/작업:** WS-05,ENG-05,PRD 안전 불변조건 → RB-19/20. 취약점 악용이나 credential 수집 절차는 이 감사에 포함하지 않는다.

### AF-09 — 재현 환경과 외부 협업 상태가 완전히 확인되지 않음

- **문제·증거/코드:** E16/17/20. 설치 버전과 CI 버전이 다르고 actual active sidecar 조합 미확인. gh/인증 connector 없음, 공개 PR/issue/actions 접근 실패, 현재 UI 오류 페이지 접근 제한.
- **사용자/사업 영향:** “내 PC에서 됨”, “push/CI 완료”의 범위를 믿기 어렵다. **기술 영향:** 환경·권한 blocker를 제품 결함과 혼동할 수 있음.
- **심각도/발생 가능성/신뢰도:** P1 / 현재 감사에서 관찰 / 확인됨·높음. 버전 혼재 자체가 버그라는 결론 아님.
- **근본 원인:** 지원 조합·실행 receipt와 remote 증거가 별도 관리되지 않음. **임시 대응:** 미확인을 표시, 재시도/우회 중단. **근본 해결:** 다음 실행의 지원 프로필·사전 상태와 remote 중복 확인을 분리 기록.

## 시험 구조 판정

테스트 파일은 충분히 존재하지만 실행 가능한 최신 결과를 이번 감사에서 수집하지 않았다. 계약/단위 회귀, 고정 모델 integration, 대화형 native 인수, production release 인수를 별도 층으로 기록해야 한다. mock은 CPU-only contract 시험에서 유효하다. **mock 통과를 XG5000 실행 성공으로 대체하지 않는 것**이 기준이지 mock을 모두 없애는 것이 아니다.

새 구현이 검증 가능한 상태가 되려면 RB-04/05가 먼저 red/green 계약을 만들고, RB-10/11에서 실제 수정 source 증거, RB-15/16에서 사용자 여정·일반화 증거가 필요하다. 이 감사만으로 제품은 합격하지 않는다.
