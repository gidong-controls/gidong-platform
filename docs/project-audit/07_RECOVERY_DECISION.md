# 07. 복구 전략과 필수 구조 교체 결정

2026-09-20 후속 지시 반영: “애매하게 남기지 말고 구조적으로 문제 있는 것은 확실히 쳐내게.” **E: 확인된 결함 경로의 제거·교체를 다음 구현의 필수 범위로 확정한다.** B(Goal 재작성), C(PRD delta)는 보조 조치다. 제거 필요성을 다시 승인 대기나 선택적 개선으로 돌리지 않는다. 다만 이번 요청은 핸드오프 보완이므로 실제 코드 변경·삭제·데이터 이전은 하지 않는다.

## 왜 E인가

이미 일반 모델 도구 루프, Host 권위·영속성·broker, native 생성/변경/저장/시험 경로가 존재한다(E03~E11). 확인된 단절은 신규 planning의 도구/완료 제어, compiler 정책 혼재, 수정 source와 immutable native attempt의 통합이다(AF-01/02/03). 따라서 전면 재작성보다 이 경계를 연결·수정하는 접근이 근거에 맞는다. 가독성·동작 반례·CI도 함께 닫아야 하며 구조 작업만 끝났다고 제품 합격을 선언하지 않는다.

## 필수 제거·교체 목록

아래 SC-01~06은 선택 사항이 아니다. **각 항목은 이전 동작의 제거 증거와 대체 경로의 동작 증거를 모두 갖춰야 닫는다.** 사용자 데이터·이력 보존과 결함 코드 보존은 다르다. 기존 모듈의 이름이나 위치를 유지하기 위해 결함 경로를 남기지 않는다.

### 제거 완료 판정 규칙

1. 제거 대상의 **기존 진입점·호출자·flag/fallback·test 기대값 → 대체 경로** 대응표를 해당 PR에 남긴다. 파일 전체를 지우는 것이 아니라 결함 동작의 도달 가능한 경로를 없애는 것이 기준이다.
2. 새 경로 추가만으로 닫지 않는다. 일반 사용자 실행 경로가 과거 결함 동작으로 돌아갈 수 있으면 미완료다. 같은 제약을 새 이름의 guard/validator로 옮기는 것도 실패다.
3. 임시 호환 처리는 기존 데이터/이력 읽기·명시적 이전에만 격리한다. 소유자·허용 호출자·제거 시점이 없거나 신규 실행을 예전 경로로 보내면 허용하지 않는다.
4. 기존 구현을 그대로 재사용할지는 해당 계약 시험으로 결정한다. 반복적으로 계약을 위반하는 구현은 관련 함수/모듈을 교체한다. “기존 기반 보존”은 코드 전부 보존하라는 지시가 아니다.
5. SC-01~06 중 하나라도 검증을 못 했으면 그 항목은 미완료/blocked다. 문구를 “개선 기회”로 바꾸거나 다른 테스트 성공으로 대체하지 않는다. **감사 문서의 완료와 이 구조 교체의 완료는 별개다.**
6. 아직 증거가 없는 장애·삭제 후보를 확정 결함으로 승격하지 않는다. 실제 vendor legality, 권한/원본 보호, immutable journal을 결함과 함께 제거하지 않는다.

## 선택하지 않은 대안

| 대안 | 선택하지 않는 이유 |
|---|---|
| A 작은 수정만 | 토큰/timeout/개수 제한 조절은 제어·source identity 충돌을 해결하지 못함 |
| B Goal만 수정 | 필요한 보조 조치이나 코드의 confirmed 제약은 남음 |
| C PRD만 수정 | 요구를 코드에 맞춰 낮추면 PLC Agent의 가치 훼손 |
| D MVP 대폭 축소 | 범위를 명시할 필요는 있으나 래더 작성/수정 책임을 모델에서 빼거나 인덱스 템플릿으로 축소할 근거 없음 |
| F 핵심 아키텍처 전면 변경 | Host/broker/store/native 기반을 버릴 근거가 없음 |

| H 요구 폐기 | 물리/SSH/production gate 분리는 기존 범위 정리이지 핵심 목표 폐기가 아님 |
| I 현재 방식 영구 중단 | 활동 중심 반복은 중단하되 제품 복구 가능성은 있음. 감사 후 승인된 작업으로 재개 가능 |

## 확정된 구조 방향과 남은 결정

- **D-01 / RB-01:** [01](01_PROJECT_INTENT.md)의 오프라인 네 여정, 실제 장비/CPU, 지원 모델/서버, 200k 해석, 인수 oracle·담당자·시간 예산. PRD27개 요구를 없애지 않고 delta만 승인한다.
- **D-02 / RB-02 — 구조 원칙 확정, 인터페이스 구체화:** 모델은 다음 도구/설계를 판단, Host는 권한/타입/identity/실행 정확성을 담당. task/working copy는 지속, source/revision/attempt는 구별. drift 시 조회·재기준 선택, 무단 overwrite 금지. SC-01~06을 남길지 여부는 결정 대기 항목이 아니다.
- **D-03 / RB-19/20:** OS secret 저장·기존 값 이동 실패 처리, 데이터/로그/백업의 수명주기.
- **D-04 / RB-22:** 개발 MVP와 production 출시 분리 및 artifact/저작·서명 책임자.

D-01의 실제 장비 의미/지원 수치와 D-03/04의 데이터·출시 결정은 여전히 별도 확인이 필요하다. 반면 사용자가 요구한 **확인된 구조 결함 제거는 필수 범위**다. RB-02는 그 필요성을 재심사하는 작업이 아니라 호출·상태 계약을 구체화하는 작업이다. 서로 무관한 미결 사항으로 구조 교체를 전부 보류하지 않는다. 이번 지시를 실제 PLC 조작·secret 이전·프로덕션 코드 변경의 즉시 승인으로 넓히지 않는다.

## MVP·성공 판정

복구 범위는 [01](01_PROJECT_INTENT.md)와 [09](09_REPLACEMENT_GOAL.md)의 자연어→작업물→실제 적용→실패 관측→일반 편집→수정본 저장/readback/재시험→읽을 수 있는 결과물이다. 후속 변경·중단/재시작·다른 구조 장비·지원 provider/장문·credential 보호까지 해당 필수 작업을 인수한다.

성공은 **합의된 corpus와 불변조건이 모두 증거로 충족**되었을 때다. model tool-call transcript, workspace/source revision, native receipt, 재열기 정보와 scenario 결과를 같은 실행 manifest에 묶는다. planner valid, 단위 test green, 8개 과거 시나리오만으로 종료하지 않는다. 모델이 필요할 때 사용자에게 요구를 묻는 것은 정상이며, 개발자가 몰래 rung을 고쳐주는 것은 자율 완료 증거가 아니다.

## 롤백 지점·작업 통제

- 최초 네 HEAD와 문서 SHA는 [10](10_EVIDENCE_INDEX.md)에 있다. 현재 사용자 문서 변경은 그대로 보존한다.
- 다음 구현은 작업별 작은 변경/PR로 분리한다. 공유 runtime.py/native_projects.py/App.tsx는 한 시점에 한 작업 소유자가 편집한다. 독립 읽기/검토는 병렬 가능.
- 잘못된 구현은 **해당 작업의 변경만 검토 후 되돌림**. 사용자 작업물·DB·native 프로젝트를 Git reset/clean으로 되돌리지 않는다. source/receipt/history는 파괴하지 않는다.
- 재시도 규칙: 같은 명령/가설이 새 정보 없이 두 번 실패하면 중단·근거 기록·다른 가설 검증. 오류를 숨기는 fallback, 무기한 timeout, test 기대값 약화 금지.
- 이번 감사 산출물은 로컬이며 commit/push/외부 이슈 생성은 하지 않았다. 구현은 새로운 사용자 지시와 Wave0 결정 확인 뒤 시작한다.
